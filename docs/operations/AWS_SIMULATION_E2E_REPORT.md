Date: 2026-11-26. Nothing in this document has been executed. No AWS resource, certificate, Production secret or MQTT flag was touched. All facts come from the repository and `DESKTOP_TWIN_AI_HANDOFF_20261124.md`, `aws-iot-so101.md`, `infra/terraform/iot/`. Healthy AWS services are **not** E2E acceptance; this plan is what would earn it.

## Goal

Prove, with an isolated test identity, the chain: Student/Web → API → IoT Core command → edge runtime (fake follower, `MOCK_RUNTIME`) → ack/status → SQS feedback worker → API lifecycle → telemetry → Digital Twin → recording upload → S3 manifest → SQS → recordings worker → `learning_experiment_artifacts` → instructor download. Classification stays `SIMULATION` / `MOCK_RUNTIME`; never `PHYSICAL_ROBOT`.

## Why not reuse the Production Thing

Production has a deployed feedback worker and recordings worker on the single EC2 reading the shared queues, with `VISTA_IOT_ENABLED=false`. A test command published for the Production Thing would (a) require turning Production MQTT on and (b) be consumed by the Production worker against the Production database, where the test `commandId` does not exist (poison message / DLQ). Existing Thing `vista-demo-f1c066c4-…` has no certificate attached and must stay that way.

## Proposed minimum scope (Option A, recommended)

The IoT Terraform root derives every name from `robot_id` (Thing, policy, rule, feedback queue + DLQ, recordings bucket via `recordings_bucket_name`). A second instance gives a fully isolated set, all pay-per-use, **no fixed-cost resource** (no EC2/RDS/NAT/ALB/ASG/MSK/GPU/SageMaker):

| Item | Value |
|---|---|
| Test robot id | a fresh UUID generated by the owner, inserted only in a **local disposable** database as the test robot |
| Thing / policy / rule / queues | `vista-e2e-<uuid>`, `…-policy`, topic rule → `…-feedback` (+ DLQ) — created by `terraform apply` of `infra/terraform/iot` with `-var robot_id=<uuid> -var environment=e2e -var recordings_bucket_name=<unique e2e bucket>` and a **separate state key** `vista/e2e/iot.tfstate` |
| Certificate | one cert created on the owner's workstation; private key never in Git, Terraform state, CI or the API secret; attach cert ↔ test Thing ↔ test policy; Amazon Root CA |
| Where it runs | API, feedback worker, recordings worker, R1 + CHECKIK fake follower, Digital Twin: **on the workstation, loopback**, against a disposable PostgreSQL and the e2e AWS resources. Production API, DB, EC2 and Production Twin are not involved in stage 1 |
| API/worker env (local only) | `VISTA_IOT_ENABLED=true`, `VISTA_IOT_DATA_ENDPOINT`, `VISTA_IOT_TOPIC_PREFIX`, `VISTA_IOT_FEEDBACK_WORKER_ENABLED=true`, `VISTA_IOT_FEEDBACK_QUEUE_URL=<e2e queue>`, `ROBOT_RECORDINGS_BUCKET=<e2e bucket>`, `ROBOT_RECORDINGS_EVENTS_QUEUE_URL=<e2e queue>`, `VISTA_RECORDINGS_WORKER_ENABLED=true`, `VISTA_PHYSICAL_RUNTIME_MODES` empty |
| Edge config | `iot.enabled=true`, `fakeRobot=true`, `hardwareEnabled=false`, `deviceShadow` on |

## Exact permissions

1. **Terraform operator (owner)**: apply/destroy on the e2e IoT root only (IoT Thing/Policy/TopicRule, IAM role for the rule, SQS ×4, S3 e2e bucket + policy/notification). Nothing in the main root changes.
2. **Local API/workers principal** (short-lived credentials, e.g. an STS session with an inline policy): `iot:Publish` on exactly `topic/vista/e2e/robots/<uuid>/commands`; `sqs:ReceiveMessage/DeleteMessage/ChangeMessageVisibility/GetQueueAttributes` on the two e2e queues; `s3:PutObject/GetObject/HeadObject` on `arn:…:<e2e bucket>/episodes/<uuid>/*`.
3. **Edge**: only the Thing policy already in the repo (connect as that Thing, publish ack/status/telemetry, subscribe/receive commands, own classic shadow).

## Test procedure and acceptance criteria

1. Edge connects; Device Shadow shows `MOCK_RUNTIME`, `hardwareEnabled:false`.
2. Student runs the qualified program from the Web UI → API creates command (`pending_publish → publishing → queued`); edge ack `accepted` → `acknowledged`; status `executing` → `completed` (`eventId`, `sequence`, `occurredAtMs` present and ordered; duplicate delivery idempotent; expired command never executed).
3. Telemetry: joint order/units per Twin schema v1, `source_mode` `SIMULATION`; authorized viewer scope; viewer without scope closed with 4403.
4. Desktop/edge recording: presign → upload files → upload `manifest.json` last (`vista.robot.recording.v1`) → S3 event → SQS → worker verifies size + SHA-256 → artifacts registered; re-delivery idempotent; mismatch rejected; DLQs empty.
5. Instructor of the submission's classroom downloads; peer and foreign teacher refused.
6. Negative: replayed sequence, expired TTL, wrong robot id, tampered manifest, missing file (retry → DLQ).
7. Evidence captured to `AWS_SIMULATION_E2E_REPORT.md` (this file, results section) with API responses, queue depths, S3 keys and SHA-256.

## Cleanup and rollback

`terraform destroy` of the e2e root (separate state; the Production IoT root and main root are untouched); deactivate and delete the test certificate, detach policy; empty and delete the e2e bucket; revoke the STS session; delete the local disposable DB. Production flags are never changed, so no Production rollback is needed.
