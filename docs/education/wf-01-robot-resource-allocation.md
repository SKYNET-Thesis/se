# WF-01 Robot Resource Allocation

School Admins may allocate only a Robot Resource entitled to their classroom's organization. The allocation is a standing authorization, not runtime execution, booking, or reservation. A classroom has one allocation; allocating another eligible robot atomically replaces it. The current implementation does not create runtime sessions, command CHECKIK, or move hardware.

See `wf-01-robot-resource-allocation.puml` for the implemented flow.

## Refinement 2026-11-27: Robot Resource management, many-to-many allocation and the Classroom Lab Session

This refines WF-01 (allocation) and the authorization step of WF-03 (execution). It is not a new capstone workflow, and WF-01..WF-04 keep their names and behaviour. Source: staged migration `database/staged-migrations/20261127_s_classroom_lab_sessions.sql`, `LabSessionService`, `RobotResourceService`, `EducationAdminService.allocateRobot/removeRobotAllocation`, `PhysicalExecutionService.resolveScope`.

### Responsibilities
| Actor | May | May not |
|---|---|---|
| System Admin | Register/edit/disable/retire a logical Robot Resource (`robots`), grant/revoke an organization entitlement (`org_entitlements`), inspect allocations and open sessions | Create AWS infrastructure, certificates or credentials from the UI; delete a resource or entitlement (history is kept) |
| School Admin | See robots entitled to their organization, allocate/remove them to its classrooms, controlled Force End of an abandoned session of its own organization (reason + confirmation) | Create global resources, grant entitlements, start a session, override a physical safety state |
| Instructor (classroom teacher with `education.lab_session.manage`) | Start, extend, end a Lab Session of a classroom they teach | Reserve a robot that is not allocated/entitled/available, or that another classroom holds |
| Student | Run on the robot **only** while their classroom holds an open session | Create, extend or end a session |

### Rules
- **Entitlement** (organization may use the resource) → **Allocation** (classroom is eligible; many-to-many: `UNIQUE(classroom_id, robot_id)`, `robot_id` not unique) → **Lab Session** (one classroom holds the robot exclusively for a bounded, supervised period). Allocation never grants control.
- **Layer A** — at most one open (`active`, `terminating`, `quarantined`) reservation per robot across all classrooms and organizations: partial unique index `ux_classroom_lab_sessions_one_open_per_robot` plus the per-robot advisory lock `hashtextextended(robot,0)` that `PhysicalExecutionService.prepare()` already takes. **Layer B** — at most one unfinished individual control session per robot (existing `control_sessions` rule, unchanged). Start Lab Session, a student Run and End/expiry therefore serialize.
- Starting a session **never arms hardware and never sends a command**; it reserves. Duration: default 120 min (`VISTA_LAB_SESSION_DEFAULT_MINUTES`), extension 5–60 min (`…_MAX_EXTENSION_MINUTES`), total ≤ 480 min (`…_MAX_TOTAL_MINUTES`). Expiry is judged on database time.
- Student start additionally requires an open session of the student's classroom for the allocated robot: `LAB_SESSION_NOT_ACTIVE` (none), `ROBOT_RESERVED_BY_ANOTHER_CLASSROOM` (another classroom holds it; the other classroom is never named). All existing checks stay: authentication, membership, assignment, Blockly prerequisite, entitlement, allocation, safety profile, runtime readiness, command authorization.
- **Disconnects.** Student stop/logout/disconnect finalizes only the individual control session; the reservation stays and another student of the same classroom may start once control is released. Edge/robot disconnect blocks new execution (existing watchdog and safe stop), keeps the reservation, never transfers it and never resumes motion on reconnect. Emergency Stop does not release the reservation.
- **End / Force End / expiry / entitlement revocation / robot disabled** use one idempotent controlled termination: `active → terminating` (no new runs), ask the runtime to stop an unfinished run, release (`released`) **only when the robot has no unfinished control session**. If the runtime cannot confirm the stop the session becomes `quarantined` (robot stays blocked, "Retry release" / recovery message); there is no force unlock. Removing an allocation while the classroom holds an open session is refused (`LAB_SESSION_OPEN`).
- Derived robot states for the UI (separate fields on the server: connectivity, reservation, control ownership, safety): Offline, Available, Reserved for this classroom, Reserved by another classroom, In use, Ending session, Safety blocked, Unavailable.

### API
`GET/POST /classrooms/:id/lab-sessions`, `GET /classrooms/:id/lab-robots`, `POST /lab-sessions/:id/{extend,end,force-end}`; `POST/DELETE /education-admin/classrooms/:id/robot-allocations[/:robotId]` (the old `PUT …/robot-allocation` remains and now adds); `GET/POST/PATCH /education-admin/robots`, `POST/DELETE /education-admin/robots/:id/entitlements[/:entitlementId]`. ### Stop Execution vs End Lab Session vs Emergency Stop (2026-11-27)
| Operation | Who / where | Effect | Releases the reservation? |
|---|---|---|---|
| **Stop Execution** | Instructor of the session (`POST /lab-sessions/:id/stop-execution`) | Asks the runtime to stop the student's CURRENT run only; the Lab Session stays active | No. The next student may start only after the run's terminal status releases the individual control session (Layer B) |
| **End Lab Session** | Instructor (`/end`), School Admin (`/force-end`, reason required), expiry, entitlement revocation, robot disabled | `active → terminating`, no new runs, stop requested for an unfinished run, release only when the robot has no unfinished control session, else `quarantined` | Yes, only after safe release |
| **Emergency Stop** | Local Edge safety mechanism (Desktop Safety Controller / physical stop), never cloud-dependent | Latches the robot stopped; explicit reset and local re-arming required | No. It never transfers or ends classroom ownership |

**MQTT cancel contract (minimal, backwards compatible).** Same commands topic, envelope, TTL, sequence and dedupe rules as a run command: `{schemaVersion:1, kind:"cancel", commandId, robotId, sequence, issuedAtMs, expiresAtMs, payload:{targetCommandId, runId, reason}}`. The Edge binds it to this robot, to the target command's own run and to a run that is still active; a stale, wrong-run, wrong-robot, duplicate or expired cancel is rejected (ACK `rejected`, code `cancel_target_unknown|cancel_target_mismatch|cancel_target_not_active|command_replayed|command_expired|command_payload_invalid`) and can never stop a later run. ACK `accepted` only means the request was accepted. **Neither the ACK nor any cloud-side event is proof of a stop**: the API releases control only when the target command reaches its terminal status (`failed`, code `cancelled`/`stopped`) published by the Edge *after* its local safe stop is confirmed. An Edge that does not implement `cancel` rejects it, which is safe (the session stays `terminating` or `quarantined`). The API publishes one cancel per experiment (audit event `lab_session_cancel_requested`) and never changes the lifecycle itself. Offline runtime or failed publish → `quarantined`.
Implemented and tested: Education API (publish, idempotency, binding) and the R1 simulation runtime. **Not implemented: Desktop physical stop** (task for Codex below). Full physical stop is not claimed.

### Release sequence, workflow support and forward recovery (2026-11-27)
**What the existing workflow supports (verified in `backend-ci.yml`, `production_db_release.py`):** the schema gate (`compat`) only requires that migrations in the image's *manifest* are in the Production ledger. Migration S is staged (not in the manifest), so the new API passes the gate and deploys on the old schema (supported combination). Education CI deploys API and Web as two `aws-demo`-approved jobs, so the owner approves `deploy-api` first and holds `deploy-web` until after S. **What it does not support:** applying S in Production. Staged migrations are rejected by the release workflow; S needs a *promotion* change (separate small PR, after #243 is deployed): move the SQL into `database/migrations/` with its manifest entry (two-commit procedure), define release scope `S` in `database/release-scopes.json` (`requiresApplied` = through `20261120_q_media_archive`) with a registered postflight verifier (pinned catalog delta: 1 table, 3 indexes, 1 constraint swap, 1 permission grant), add it to the Production Database Release scope choices, regenerate the dev schema expectation. After promotion the manifest requires S, so the schema gate will correctly refuse any later deploy until S is applied (that is the intended fail-closed behaviour).
**Sequence:** (1) verified backup (`check-backup`) and recovery readiness; (2) merge #243, approve `deploy-api` (leave `deploy-web` pending); (3) verify health, an existing allocation, and that `GET /classrooms/:id/lab-robots` answers 503 `LAB_SESSION_SCHEMA_NOT_READY`; (4) promotion PR merged, then Production Database Release scope `S` with its reviewer approvals; (5) postflight verification (table, indexes, constraint swap, permission) and Lab Session endpoints answering 200; (6) approve `deploy-web`; (7) Production Lab Session acceptance.
**After S — no accidental rollback to `f0b3d87`.** Education CI `action=rollback` is deliberately not schema-gated, so run the read-only guard first and treat a failure as a stop: `python scripts/production_db_release.py rollback-guard --expected-project-ref <ref>` (reader credentials only; tested in `tests/database/test_rollback_guard.py`). It refuses as soon as `classroom_lab_sessions` exists. Wiring the guard into the workflow itself changes the reviewed gate structure enforced by `check_database_workflow_safety.py`, so it is left as a proposed owner-reviewed change rather than made silently.
**Forward recovery (post-S):** never redeploy a pre-S image. Compatible rollback targets are only images built from #243 or later (they tolerate both schemas). To undo an API change, redeploy the previous Lab-Session-aware image; to remove a bad reservation, End/Force End it; to reduce a classroom to one robot, remove allocations through the product. Allocations and Lab Session history are never deleted to restore the old constraint, and the rollback SQL is refused by PostgreSQL while any classroom holds several robots (tested).

### Safe-stop confirmation (release after cancellation)
A reservation is released only when (a) the robot has no unfinished control session **and** (b) the stop is trustworthy. A cloud-side terminal state — `timed_out` (no answer) or `reconciliation_required` (publish outcome unknown) — never establishes that the hardware stopped: the session is held `quarantined` unless a connected Edge Device Shadow, reported after the cloud gave up, shows no active run (`LabSessionService.edgeStopUnconfirmed`, tested in `lab-session-safe-stop.spec.ts`; an unreadable Shadow also blocks). An Edge-published terminal status (`completed`/`failed`) after the cancel is accepted. For physical mode the Desktop must publish that terminal status only after its own local safe-stop verification (handoff §14). Residual: the individual student control-session rule (Layer B) is unchanged; its behaviour for a cloud-only timeout should be reviewed together with the physical commissioning checklist.
